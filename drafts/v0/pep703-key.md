PEP 703 为了在 CPython 中彻底移除全局解释器锁（GIL），对整个运行时的底层架构进行了全方位的改造。这些改动可以归纳为**五大核心支柱**：

```
                       ┌─── 1. 引用计数体系 (偏置 / 延迟 / 永生 / 堆类型分散计数)
                       ├─── 2. 内存底座重构 (mimalloc 替换 / 剔除链表指针 / 线程私有缓存)
PEP 703 五大核心支柱 ───┼─── 3. 垃圾回收重建 (主动式 STW 挂起协议 / 彻底废除分代回收)
                       ├─── 4. 容器与数据并发 (单对象微锁 / 防死锁临界区 / 乐观无锁读与 RCU)
                       └─── 5. 执行引擎与生态过渡 (特化并发保护 / 借用引用安全化 / 兼容保护阀)
```

---

### 一、 引用计数体系重构

多核并发运行时，直接对单一计数器执行硬件级原子加减会导致 CPU 缓存行剧烈冲突。PEP 703 组合了四项技术来分流压力：

1. **偏置引用计数（Biased Reference Counting, BRC）**
   * **所有权划分**：对象区分“创建它的主人线程”与“外部借用线程”。主人修改本地计数（`ob_ref_local`）走单周期非原子指令；外部线程修改共享计数（`ob_ref_shared`）走 CPU 原子指令。
   * **单向状态机**：通过共享计数字段的低 2 位维护 `Default → Weakrefs → Queued → Merged` 状态，确保未被跨线程共享的私有对象能够直接走无锁的极速销毁通道。
2. **延迟引用计数（Deferred Reference Counting）**
   * **跳过栈操作**：函数、代码块（Code Object）、模块等高频共享对象在被线程的执行栈压入或弹出时，**完全跳过计数器的增减**，彻底消除调用热点函数时的总线拥堵。
   * **推迟生死判决**：这类对象的释放被推迟到垃圾回收（GC）阶段。GC 在暂停所有线程后统一扫描各线程调用栈，累加出真实引用数，确认无人使用后才销毁。
3. **永生化对象（Immortalization）**
   * 将 `None`、`True`、`False`、小整数和全局静态类型标记为永生状态（计数器设为最大值）。
   * 运行时代绝对忽略它们的增加和减少操作，消除最基础对象的跨核数据竞争。
4. **堆类型对象的分散引用计数（Per-thread Type Counts）**
   * 用户自定义类（Heap Type）会被大量实例频繁引用。若每个实例创建都去修改类对象的计数器，会造成严重的读写冲突。
   * 解决方案是让每个线程维护一个私有的局部数组，分别记录本线程持有的各个类实例数量，GC 运行时汇总所有线程的数组来确定类型的生命周期。

### 二、 内存底座重构

老 Python 的内部内存分配器 `pymalloc` 是基于单线程假设编写的，在多线程并发下无法保证安全与性能。

1. **全面换用微软 `mimalloc` 分配器**
   * 用成熟的高性能开源分配器 `mimalloc` 替代 `pymalloc`，原生提供跨线程无锁分配能力，并按对象大小划分子页面，兼顾速度与内存碎片控制。
2. **顺藤摸瓜找对象（移除 GC 链表指针）**
   * 以前所有需要循环垃圾回收的对象必须带上 `_gc_prev` 和 `_gc_next` 指针，串在全局双向链表上，多线程同时插入/移除链表会带来严重的锁竞争。
   * PEP 703 彻底砍掉了这两个指针（每个对象节省 16 字节），转而直接借助 `mimalloc` 内存页本身的层级结构遍历堆上分配的所有对象。
3. **空闲缓冲池线程私有化（Thread-Local Free Lists）**
   * 以前用于加速微小对象（如浮点数、小列表、空元组）复用的全局空闲列表，全部转移到各个线程的私有数据结构（`PyThreadState`）中。各线程只复用自己丢弃的对象，互不干扰。
   * 严格区分 Python 对象分配接口（`PyObject_Malloc`）与纯系统内存分配接口，确保同一内存页复用时对象头部的结构与偏移量始终保持一致。

### 三、 垃圾回收体系重建

在多核并行执行字节码的环境下，旧版垃圾回收的安全性与性能模型均不再成立。

1. **建立主动式“停止世界（Stop-the-World, STW）”机制**
   * 引入三种明确的线程状态：`ATTACHED`（运行 Python 字节码）、`DETACHED`（脱离 Python，执行阻塞 I/O 或纯 C 计算）、`GC`（已挂起）。
   * GC 启动时，利用中断信号（`eval_breaker`）促使运行中的线程在字节码安全点主动挂起并转为 `GC` 状态；对脱离 Python 的线程则通过原子 CAS 强制标记。只有当全体线程都处于完全静止状态时，GC 才开始遍历堆。
2. **彻底废除分代垃圾回收（Non-generational GC）**
   * 取消 0 代、1 代、2 代的世代划分，转为单一世代的低频全量清理。
   * **取舍考量**：Python 绝大多数短命对象已经在引用计数归零的瞬间被实时就地释放，新生代中可回收的垃圾比例极低；如果在多核环境下依然频繁触发分代回收，每次都执行 STW 挂起会导致多线程吞吐量严重下降。单一世代回收改为在存活对象堆体积按比例膨胀时才低频触发。

### 四、 容器与数据并发安全

没有了全局锁，多个线程同时修改同一个容器（如向同一个列表执行 `append`）会导致内部指针损坏和进程崩溃。

1. **单对象 1 字节轻量锁（Per-object Mutex）**
   * 在每个 `list`、`dict`、`set` 对象头部开辟 1 个字节存储轻量互斥锁（`ob_mutex`）。
   * 凡涉及容器结构变更的操作（修改、追加、清空）均必须持有该对象的锁；单字段的读取（如 `len(list)`）则使用底层原子读取指令直取，不加锁。
2. **防死锁的 Python 临界区机制（Critical Sections）**
   * **地址排序打破死锁**：当一次操作必须同时锁定两个容器（如比较两个列表 `a == b`）时，强制先锁定内存物理地址数值较小的对象，再锁定地址较大的对象，从数学上杜绝相互等待造成的死锁。
   * **主动让出机制**：持锁线程如果需要进入阻塞等待（例如等待 I/O 或等待子操作的内部锁），运行时会自动暂挂并交出此前已拿到的外层锁，防止阻塞其他线程。
3. **列表与字典的“乐观无锁读”（Optimistic Locking & RCU）**
   * 字典和列表的单项检索极其频繁。为避免读操作也频繁争抢互斥锁，PEP 703 引入了类似 Linux 内核 RCU 的快速路径：
     * 读线程先不加锁，直接原子加载指针，并通过 `_Py_TRY_INCREF` 尝试递增对象的引用计数。
     * 加完后核对前后指针是否一致；若发生并发写导致指针改变，则主动回退到慢速加锁路径（Retry）。
   * 配合基于 FreeBSD GUS 算法的内存页版本号控制，确保在并发乐观读期间，即使相关条目被其他线程删除，底层内存页也绝不会被立即交还操作系统，杜绝内存段错误（Segmentation Fault）。

### 五、 执行引擎与生态平稳过渡

为了保证庞大的 C 扩展生态在无 GIL 时代能够安全运行并完成渐进式迁移，PEP 703 制定了专门的兼容与演进策略。

1. **废弃不安全的“借用引用（Borrowed References）”**
   * 类似 `PyList_GetItem` 这样的接口只外借指针而不增加引用计数。在无 GIL 下，若其他线程瞬间删除了该项，借出的指针会当场变为野指针。
   * 引入如 `PyList_FetchItem`、`PyDict_FetchItem` 等新接口，强制在锁保护下将引用计数递增完毕后再返回具有所有权的新引用（New Reference）。
2. **自适应特化解释器（Specializing Interpreter）的并发安全**
   * 针对运行期动态替换字节码指令并记录类型缓存（Inline Cache）的优化机制：
     * 写入特化字节码的过程必须获取互斥锁。
     * 多线程环境下每条字节码只允许特化一次，写定后不再反复变动，防止多核心读写同一缓存槽产生数据撕裂。
3. **C 扩展兼容安全阀与隔离 ABI**
   * **动态降级保底**：C 扩展模块必须显式声明 `Py_mod_gil_not_used`。如果在无 GIL 环境下加载了未做并发适配的老扩展，Python 会输出警告并**自动重新启用全局 GIL**，退回单核安全模式以防崩溃。
   * **构建标签物理隔离**：无 GIL 构建的解释器及扩展库采用独立的 ABI 标签（文件名带有 `t` 标识，如 `cp313t`），从二进制分发层面上杜绝老扩展被错误加载。
   * **环境变量强制干预**：开发者可通过 `PYTHONGIL=0` 强行禁用 GIL 运行，或通过 `PYTHONGIL=1` 强制开启 GIL 进行行为对比和调试。
